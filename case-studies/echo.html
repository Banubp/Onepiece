Design status Echo does not yet have an official interface. These diagrams explain the system concept and learning model; they are not final product screens.

The user should delegate a goal—not become the coordinator of multiple tools.

Echo is a system-design exploration of how one accountable AI relationship can plan across services, assign bounded work, request approval at the right moment and return evidence instead of unsupported claims.

01

Problem and vision

Today’s assistants can use tools, but the user still carries the coordination, verification and risk.

The orchestration gap

A simple request such as “plan a movie tonight” may depend on calendars, subscriptions, cinema availability, travel time, budget and permission to book.

When each capability behaves like a separate conversation, the user repeats context, resolves contradictions and checks whether “done” means a suggestion, a tool response or a confirmed real-world outcome.

Echo reframes the product around accountable delegation: one relationship owns the goal, specialists receive only the context and authority they need, and consequential actions return to the user for an explicit decision.

How might Echo coordinate a cross-service goal end to end while keeping authority visible, evidence traceable and the user in control of consequence?Problem statement

03

Research and principles

Translating real coordination risks into product and architecture requirements.

Scenario analysis + trust modelling

Echo’s research focus is not whether an AI feels helpful; it is whether responsibility remains understandable when planning crosses services and actions have consequences.

Research questions

  • Where does context fragment during a multi-service goal?
  • Which activities are safe to read, propose or execute?
  • What proves that a real-world outcome actually occurred?
  • How should interrupted or partially completed work recover?
  • Which memories need provenance, correction and expiry?

Design principles

  • One accountable voice owns the relationship
  • Task rooms enforce least-context and least-authority access
  • Evidence accompanies every completion claim
  • Approval appears exactly where consequence begins

05

Build process

Reliability before pretend autonomy.

Construction sequence

Each subsystem is attached through clear contracts, health checks, staged integration and recovery boundaries.

Foundation

DNA + skeleton

Terminology, identity, schemas, lifecycle state and append-only audit.

Coordination

Nervous system

Typed messaging, task rooms, correlation, cancellation and backpressure.

Reasoning

Brain + memory

Planning, provenance, confidence, expiry, correction and forgetting.

Capability

Organs + muscles

Read-only connectors first; write actions only after boundaries hold.

Protection

Immune system

Budget guards, approval gates, retries, idempotency and recovery.

Integration

Connected workflows

Real scenarios bring coordination across subsystem boundaries together.

06

Lifetime learning module

Learning continuously without turning every interaction into permanent, unverified memory.

Compounding intelligence

Echo is designed to improve across its lifetime: every task can produce evidence, corrections and reusable patterns, but nothing earns trust merely because it happened once.

Observe

Capture outcomes

Record what was attempted, what actually happened and what evidence confirms it.

Evaluate

Test before reuse

Compare predictions with outcomes, surface contradictions and lower confidence when evidence is weak.

Remember

Store bounded knowledge

Retain source, scope, confidence and expiry—not an unquestioned biography of the user.

Improve

Promote proven patterns

Reuse behaviours only after repeated success, regression checks and human correction when consequences are high.

Learning is not permission

What Echo learns can improve planning, but it never expands its authority. Spending, booking, messaging and other consequential actions still require the relevant approval boundary.

07

Experience direction

Requirements for a future interface—not a claim that the product UI is complete.

Critical states

The interface must make planning, conflict, approval, progress and interrupted actions visibly different.

Planning
User sees

Goal, constraints, assumptions and proposed steps.

User controls

Edit the plan before any execution begins.

Conflict
User sees

Clashing commitments and their consequence.

User controls

Choose, revise or ask Echo to find another path.

Approval
User sees

Exact action, destination, price and authority.

User controls

Approve once, reject or narrow permission.

Interrupted action
User sees

What completed, what paused and what still needs attention.

User controls

Resume safely without duplicating completed actions.

Future interface requirement These states define what a later interface must communicate. Visual design begins after the system contracts and real workflows are stable.
08

Reflection and next steps

The product decision that governs every layer of Echo.

Accountability before autonomy

Autonomy is not a global setting. It is a collection of narrow, reversible permissions attached to one goal.

Echo remains in active development. The immediate priorities are dependable calendar coordination, exact evidence binding, budget and approval guards, and cross-device continuation. Interface design will follow the behaviour of stable workflows rather than presenting speculative screens as a finished product.
