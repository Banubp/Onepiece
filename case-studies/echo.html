01

Problem and vision

A coordination problem disguised as an assistant problem.

Product thesis

“Plan a movie” can require calendar checks, subscriptions, cinemas, travel time, budget and a final approval.

Most assistants expose each capability as a separate interaction. The user transfers context, compares results, catches conflicts and decides which actions are safe. More tool calls do not remove the coordination burden.

Echo reframes the goal: delegate the outcome, not the project management, while keeping consequential decisions with the user.

How can one accountable intelligence coordinate bounded specialists and return one verified outcome?Product question

03

Research and principles

Turning trust concerns into structural product rules.

Failure-oriented analysis

Trust cannot be added as personality. It must exist in authority, evidence, memory and recovery contracts.

Investigation focus

  • Where context fragments across services
  • How planning and acting permissions differ
  • Why a tool success can differ from real-world success
  • How partial failure should be communicated
  • What memory must retain, expire or forget

Four product principles

  • One accountable voice
  • Bounded task rooms and least authority
  • Evidence travels with every claim
  • Approval appears at the moment of consequence

05

Build process

Reliability before pretend autonomy.

Construction sequence

Each subsystem earns attachment through contracts, health checks, failure tests and recovery evidence.

Foundation

DNA + skeleton

Terminology, identity, schemas, lifecycle state and append-only audit.

Coordination

Nervous system

Typed messaging, task rooms, correlation, cancellation and backpressure.

Reasoning

Brain + memory

Planning, provenance, confidence, expiry, correction and forgetting.

Capability

Organs + muscles

Read-only connectors first; write actions only after boundaries hold.

Protection

Immune system

Budget guards, approval gates, retries, idempotency and recovery.

Integration

Whole-body tests

Real scenarios verify coordination across subsystem boundaries.

06

Lifetime learning module

Learning continuously without turning every interaction into permanent, unverified memory.

Compounding intelligence

Echo is designed to improve across its lifetime: every task can produce evidence, corrections and reusable patterns, but nothing earns trust merely because it happened once.

Observe

Capture outcomes

Record what was attempted, what actually happened and which evidence confirms it.

Evaluate

Test before reuse

Compare predictions with outcomes, surface contradictions and lower confidence when evidence is weak.

Remember

Store bounded knowledge

Retain source, scope, confidence and expiry—not an unquestioned biography of the user.

Improve

Promote proven patterns

Reuse behaviours only after repeated success, regression checks and human correction where consequence is high.

Learning is not permission

What Echo learns can improve planning, but it never expands its authority. Spending, booking, messaging and other consequential actions still require the relevant approval boundary.

07

Experience direction

Requirements for a future interface—not a claim that the product UI is complete.

Critical states

The interface must make planning, conflict, approval, progress and partial failure visibly different.

Planning
User sees

Goal, constraints, assumptions and proposed steps.

User controls

Edit the plan before any execution begins.

Conflict
User sees

Clashing commitments and their consequence.

User controls

Choose, revise or ask Echo to find another path.

Approval
User sees

Exact action, destination, price and authority.

User controls

Approve once, reject or narrow permission.

Partial failure
User sees

What succeeded, failed and was skipped.

User controls

Retry safely without duplicating completed actions.

Future interface requirement These states define what a later interface must communicate. Visual design begins after the system contracts and real workflows are stable.
08

Testing and build evidence

What was tested, what failed and what changed because of it.

Evidence, not demo theatre

The first synthetic evaluation passed 45 tests; the real-calendar scenario delivered the more important learning.

45 testsPlan, evidence, conflict, approval, persistence and determinism.
0.2s overlapConcurrency evaluation demonstrated real worker overlap.
Approval heldIrreversible booking stayed blocked in the first release.
Real failureCalendar connector failed after three attempts and booking was skipped.
Outcome: completed with failures

The test exposed the need for partial outcomes, retry boundaries and honest completion states. The system did not hide the connector failure or claim the booking was complete.

09

Reflection and next steps

The product lesson beneath the architecture.

Key learning

Autonomy is not one slider. It is a set of small, reversible authorities granted for one goal.

The next build priorities are repairing the real calendar adapter, hardening evidence binding, adding budget guards and testing cross-device continuation. Intelligence expands only after the system can fail honestly and recover safely.
