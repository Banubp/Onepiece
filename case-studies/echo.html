Echo · AI systems · Active build

One intent. Many hands.

A personal AI colony that forms temporary specialist teams while keeping one coherent, accountable relationship with the user.

Echo is designed for goals that cross calendars, services, decisions and real-world actions—without making the user coordinate every tool.

01

The problem

A coordination problem disguised as an assistant problem

Today’s assistants answer. Life still needs orchestration.

A simple goal such as “plan a movie” can require calendar checks, subscription knowledge, cinema discovery, travel time, budget and approval.

Most assistants expose each tool as a separate interaction. The user becomes the project manager: copy context, compare outputs, catch conflicts and decide which action is safe to execute.

Echo reframes the problem from “How should an AI call more tools?” to “How can one accountable intelligence coordinate bounded specialists and return one verified outcome?”

Fragmentation

Context breaks

Calendars, subscriptions, payments and preferences live in separate systems.

Trust

Authority blurs

Automation becomes unsafe when read, plan and act permissions are treated alike.

Reliability

Success is claimed early

A tool call is not the same as a verified real-world outcome.

Echo should do the coordination work while the user retains the consequential decisions.Product thesis
02

Product principles

Authority before autonomy

Reliable first. Autonomous second.

The system cannot earn trust through personality. It earns trust by making boundaries, evidence and recovery structural.

Principle 01

One accountable voice

Only the Queen communicates final decisions to the user. Specialists cannot produce conflicting promises.

Principle 02

Bounded task rooms

Workers receive only the context and authority required for their assigned objective.

Principle 03

Evidence travels with claims

Results retain provenance, confidence, expiry and correction paths.

Principle 04

Approval at consequence

Irreversible actions wait for explicit user approval at the moment the action is ready.

03

System architecture

One connected body

Build the contracts before adding intelligence.

Every subsystem needs a contract, health check, failure mode and recovery path before it is connected to the next.

  1. 01UserStates a goal and constraints
  2. 02QueenOwns the relationship and authority
  3. 03Head WorkerPlans and coordinates a temporary colony
  4. 04SpecialistsExecute bounded tasks and return evidence
  5. 05QueenVerifies and communicates one result
Foundation

DNA + Skeleton

Terminology, identity, schemas, lifecycle state and append-only audit.

Coordination

Nervous system

Typed messaging, task rooms, correlation, cancellation and backpressure.

Reasoning

Brain + Memory

Deterministic planning, provenance, confidence, expiry, correction and forgetting.

Construction order

  • Foundations before model providers
  • Read-only connectors before write actions
  • Failure tests before the next subsystem
  • Full-body scenarios before release claims

Why this order?

Adding an LLM early would make the demo look intelligent while hiding weak contracts underneath.

04

Key decisions

Designing the invisible experience

The interface is also the trust model.

Decision 01

Separate planning from acting

Echo can explore and compare freely, but action authority is granted narrowly and explicitly.

Decision 02

One goal, temporary colony

Specialists are assembled around an outcome and dissolved afterward, limiting context contamination.

Decision 03

Memory is evidence, not biography

Stored facts carry source, confidence, scope, expiry and user correction.

Decision 04

Verify outcomes independently

Completion is based on observed evidence, not a worker’s own success claim.

Build evidence and learning

Progress is accepted through evidence

Test the body, not just the happy path.

The build uses contract tests, adversarial cases and evidence records before a subsystem is accepted.

An early synthetic movie-planning evaluation exercised planning, conflict detection, approval gating, persistence and deterministic replay. A later real-calendar test exposed the more useful truth: connectors can fail even when the rest of the system behaves correctly. That failure shaped the requirement for partial outcomes, retry boundaries and honest completion states.

The strongest product learning is that autonomy is not a single slider. It is a collection of small, reversible authorities granted for a specific goal.

The most trustworthy assistant is not the one that claims it can do everything. It is the one that knows exactly what it is allowed to do—and proves what happened.Reflection
