Spine · Product-agnostic decision framework

Reason before intervention.

A system for exposing mechanisms, leaks and weak assumptions before a team changes the product.

Spine turns design principles into inspectable reasoning: what behaviour should change, why it should change and what evidence would prove the decision wrong.

01

The problem

From principle theatre to causal reasoning

Teams remember laws. Products fail in the gaps.

“Use Hick’s Law” is not a decision. It does not explain the competing mechanisms, the expected behaviour or the business consequence.

Product critique often stops at naming a principle. That creates authority without accountability: the principle sounds correct, but the intervention can still produce a new leak elsewhere.

Spine was created to ask a harder sequence: What mechanism is operating? Where does value leak? Which hypothesis best explains it? What observation would falsify that hypothesis?

Failure 01

Principle matching

A screen is labelled with a law without tracing the mechanism.

Failure 02

Single-hypothesis bias

The first plausible explanation becomes the design direction.

Failure 03

Local optimisation

A usability gain is accepted while trust or captured value deteriorates.

The case is not solved when the interface looks better. It is solved when the mechanism changes and the evidence survives competing explanations.Framework thesis

03

The audit engine

Six passes, one defensible decision

Separate observation from interpretation.

  1. Pass 01FactsRecord only what is observed
  2. Pass 02MechanismsMap plausible causal forces
  3. Pass 03LeaksLocate lost user and business value
  4. Pass 04HypothesesCompare explanations explicitly
  5. Pass 05ExperimentChoose the highest information gain

The daylight test

  • Can another person trace the reasoning?
  • Are competing hypotheses visible?
  • Is confidence separated from certainty?
  • Would a contradictory result change the decision?

Final pass

Translate the chosen intervention into a Spine Statement with owner, evidence, falsifier and review date.

Instrument

Loophole map

Finds how a locally correct principle can be exploited or create a system-level leak.

Instrument

State and severity

Separates a transient friction from a persistent, high-consequence mechanism failure.

04

The Forge

Adding knowledge without bloating the library

A new principle must earn its place.

The five-gate Forge prevents the framework from becoming a collection of attractive but overlapping rules.

Gate 01

Distinct mechanism

Does it explain something the existing library cannot?

Gate 02

Falsifiable claim

Can an observation prove the proposed principle wrong?

Gate 03

Practical instrument

Can a team actually use it to choose or reject an intervention?

Gate 04

Boundary clarity

Are the context, failure modes and inversions explicit?

Gate 05

Evidence quality

Is support stronger than analogy or repeated citation?

Result

Admit, merge or reject

The library expands only when the principle improves reasoning coverage.

A bigger library is not a better framework. Better discrimination is.Forge principle
05

Learning loop

From static framework to evolving system

Every intervention should improve the next decision.

Spine treats outcomes as evidence that can update confidence, refine boundaries and expose missing mechanisms.

Before intervention

Competing hypotheses

List each explanation separately with confidence, supporting evidence, contradictions, missing evidence and predicted observations.

After intervention

Evidence update

Compare the result with the falsifier, revise confidence and record whether the principle transferred.

Live framework tests included a habit-product streak scenario, a fintech deposit confirmation and a food-delivery average-order-value decline. The important moments were not when Spine produced a recommendation, but when it rejected an attractive explanation because the available facts did not support it.

The next product step is to turn Spine from a framework used by an analyst into an autonomous, versioned system with memory, evidence files and an orchestrator—without allowing the system to rewrite its own standards invisibly.
